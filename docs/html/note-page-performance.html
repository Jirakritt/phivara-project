Page performance: งานค้างตรวจ (VPS render ช้า)

บันทึกเมื่อ 11 พ.ย. 2569 · สถานะ: พักไว้ก่อน รอกลับมาทำ

สรุป: ISR ใช้งานได้ครบทุกหน้าแล้ว (หน้าแรก, หน้ารายการ, หน้า slug ของ doctor/program/article/branch) แต่ตอนที่ต้อง สร้างหน้าใหม่ บน VPS ใช้เวลานานผิดปกติ

ตัวเลขที่วัดบน production (หลัง deploy f439dd6)

กรณี เวลา (TTFB)
หน้าที่อยู่ใน cache (HIT/STALE) 0.2-0.5 วินาที
สร้างหน้า slug ใหม่ครั้งแรก (MISS) 5-7 วินาที (สูงสุดที่เจอ 20 วินาที)
รันบนเครื่อง local เทียบกัน ~0.2 วินาที
/api/popup/active ส่วนใหญ่ 0.15-0.2 วินาที แต่บางครั้งช้า 2.5 / 23.9 / 31 วินาที

ก่อนแก้ ISR หน้าแรกอยู่ที่ ~3.7-4.1 วินาที ทุกครั้ง และหน้าอื่น 6-15 วินาที ทุกครั้ง

ข้อมูลที่ตรวจแล้วบน VPS ปัจจุบัน (11 พ.ย. 2569)

  • CPU 1 core (nproc = 1), RAM 3.8 GB (ใช้ ~0.8 GB ตอนปกติ), swap 2 GB (ใช้น้อย), load average 4.9-5.7 ขณะ build/มีคนเข้า (งานรอคิวมากกว่าที่ 1 core รับได้ ~5 เท่า)
  • Postgres, Next (pm2) และ next build ใช้ CPU เดียวกัน การสร้างหน้า static ตอน build จึงเกิน 60 วินาทีต่อหน้า (build ล้มเหลว 1 ครั้ง ผ่านได้บางครั้งเมื่อ retry)
  • RAM ไม่ใช่คอขวด คอขวดคือ CPU
  • แผนของทีม: จะย้ายไป server ที่มี resources มากกว่านี้ แต่ตอนนี้ใช้เครื่องนี้ไปก่อน
  • ตอนทำ TOR/สเปกเครื่องใหม่ ควรระบุ จำนวน vCPU ให้ชัด (ไม่ใช่แค่ RAM/storage) แนะนำอย่างน้อย 4 vCPU เพราะเว็บ + Postgres + การ build อยู่เครื่องเดียวกัน

สิ่งที่แก้เพื่อให้อยู่กับเครื่องเดิมได้

  • generateStaticParams ที่ [locale]/layout.tsx คืนรายการว่าง: ไม่ prerender หน้าสาธารณะตอน build แต่ละหน้าถูกสร้างตอนมีคนเข้าครั้งแรกแล้ว cache (ISR ยังทำงานเหมือนเดิม) build จึงเร็วและไม่ชนเพดาน 60 วินาที
  • staticPageGenerationTimeout: 180 ใน next.config.mjs เป็นตัวกันเหนียว
  • scripts/warm-cache.sh: หลัง deploy รันเพื่อเรียกทุกหน้าใน sitemap ทีละหน้า (ทีละหน้าเพราะมี 1 core) ให้ cache อุ่นก่อนผู้ใช้จริงเข้า
  • เมื่อย้ายเครื่องใหม่แล้ว วิธีเหล่านี้ยังใช้ได้ ปรับกลับไป prerender ตอน build ได้ถ้าต้องการ (เปลี่ยน generateStaticParams ให้คืน th/en)

สิ่งที่สงสัย (ยังไม่ได้ตรวจ ห้ามสรุปว่าเป็นสาเหตุ)

  • ~~CPU ของ VPS เป็นคอขวด~~ ยืนยันแล้ว: เครื่องมี 1 core ดูหัวข้อด้านบน
  • DB/query ช้า หรือจำนวน query ต่อหน้าเยอะ
  • popup API ช้าเป็นช่วงๆ หลังเซิร์ฟเวอร์สร้างหลายหน้าพร้อมกัน

ตอนกลับมาทำ เริ่มจาก

  1. ตรวจบน VPS (อ่านอย่างเดียว): nproc, free -h, top/htop ขณะเรียกหน้า, pm2 logs, เวลา query DB
  2. Prerender slug จริงตอน build (ดึง slug จาก DB ใน generateStaticParams) ให้ผู้เข้าชมคนแรกไม่ต้องรอ แลกกับ build นานขึ้น
  3. ลดจำนวน query ต่อหน้า ถ้าพบว่าเยอะเกินจำเป็น
  4. วัดคะแนน PageSpeed ใหม่ (รอบก่อน quota API เต็ม ใช้ pagespeed.web.dev แทนได้)
