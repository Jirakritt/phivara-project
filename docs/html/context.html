2. ข้อจำกัดในการทำงานกับ Claude (สำคัญ)

  • Claude แก้ไฟล์ในโปรเจกต์ได้โดยตรง แต่ ไม่มีสิทธิ์เข้า SSH/VPS, production DB หรือ git push
  • งานฝั่ง server ทั้งหมด (git pull, migrate, build, pm2, backup, SQL) ผู้ใช้รันเอง แล้ววางผลลัพธ์ให้ Claude ตรวจ ทีละขั้น
  • Claude ไม่เขียน .env จริง — บอกบรรทัดที่ต้องเพิ่มแทน (.env.example แก้ได้)
  • ผู้ใช้ชอบให้ ตรวจใน local ก่อน commit/deploy และชอบ "วางแผน → confirm → ลงมือ" สำหรับงานใหญ่
  • ตอบเป็นภาษาไทย

3. กฎ/บทเรียนที่ได้มาแบบเจ็บตัว (ห้ามลืม)

Deploy

  1. ลำดับบน production: pull → migrate → build → pm2 reload — ต้อง migrate ก่อน build เพราะ next build prerender หน้า (เช่น /sitemap.xml) โดยยิง DB จริง ถ้า schema ยังไม่มีจะ build พัง (เคยพลาดครั้งหนึ่ง กู้ได้โดยไม่เสียข้อมูล)
  2. Backup DB ทุกครั้งก่อน migrate และ tag git HEAD เป็นจุด rollback — pg_dump ต้องดึง URI จาก .env ตรงๆ ($DATABASE_URI ไม่ได้ export ใน shell): pg_dump --format=custom "$(grep '^DATABASE_URI=' .env | cut -d '=' -f2-)" > backup.dump
  3. ใช้ npx payload migrate ตรงๆ ใน terminal ที่โต้ตอบได้ — npm run migrate จะเงียบ (no-op) ถ้า Payload ถามยืนยัน ("data loss will occur…") ซึ่งเป็นคำเตือนทั่วไปเพราะเคยใช้ dev-push กับ DB นั้น ให้อ่าน SQL ใน migration ว่าเป็น additive จริงก่อนตอบ yes
  4. payload migrate:create เทียบกับ snapshot journal ของ migration เก่า ไม่ได้ introspect DB จริง — ถ้า DB เคยถูก dev-push (next dev push mode สร้างแถว dev, batch -1) จะเจอ error "already exists" ให้ตรวจ schema จริงก่อน แล้วค่อย reconcile payload_migrations ด้วย INSERT ตาม DEPLOY.md Part 4.1 (ห้ามเดา)
  5. สร้าง migration ต้องทำบนเครื่อง Mac ของผู้ใช้ที่ DB local ถูก sync แล้ว (sandbox ของ Claude รัน tsx/esbuild ไม่ได้ — platform ไม่ตรง และต่อ DB ไม่ได้)
  6. ถ้าแก้ไฟล์ generated บน server เพี้ยน ให้ git checkout -- <file> กู้ อย่า hand-patch

Payload

  • update() validate ทั้ง document ทุกครั้ง → script ที่แก้ field เดียวอาจ FAILED เพราะคำแปลที่ยังไม่ครบใน field อื่น (เห็นตอน backfill หมอ 143 รายการ — ไม่ block และไม่ได้เกิดจากโค้ดใหม่)
  • field แบบ hasMany relationship ครั้งแรกของ collection จะสร้างตาราง <collection>_rels ใหม่ (+ ตาราง _v_ สำหรับ drafts)
  • Unpublish ผ่านเมนูใน admin เคยไม่ทำงาน → ใช้ REST: PATCH /api/doctors/<id> body {"_status":"draft"}

CSS

  • เว็บโหลด 3 stylesheet (main.css, main_gpt.css, site-shell.css) โดย site-shell.css โหลดท้ายสุดและชนะ — แก้ main.css อย่างเดียวอาจไม่มีผล
  • site-shell.css มี reset บังคับ font-size ขั้นต่ำของ p/a/strong; ถ้าต้องการขนาดเฉพาะให้ใส่ class phivara-type-size-override (มีใช้อยู่แล้วที่ program/[slug]/page.tsx)
  • ผู้ใช้ทำ pass ปรับ font-size ทั้งเว็บเป็น ≥16px เพื่ออ่านง่าย (commit ช่วง 22–23 ก.ย.) — งานใหม่ควรคง baseline นี้

5B. SEO / Google Search Console (พ.ย. 2569)

  • ยืนยันโดเมน phivaraphyathai.com ใน Search Console ด้วย TXT record ที่ DNS (Hostinger, nameserver *.dns-parking.com) ห้ามลบ TXT นี้; ส่ง https://www.phivaraphyathai.com/sitemap.xml แล้ว (สถานะ Couldn't fetch ช่วงแรกเป็นเรื่องปกติ ตรวจซ้ำ)
  • พบ "Duplicate, Google chose different canonical" ที่ /th: Google เลือก / เป็น canonical เพราะ redirect หน้ารากเป็น 307 ชั่วคราว → แก้เป็น 308 ใน src/middleware.ts + เพิ่ม hreflang (th/en/x-default) ที่หน้าแรก ((public)/page.tsx generateMetadata)
  • โดเมนไม่มี www เคยตอบ 200 ซ้ำกับ www → ต้อง 301 ไป www ที่ nginx (ดู DEPLOY.md หัวข้อ redirect ไม่มี www)
  • หลัง deploy ให้ Request indexing /th และ /en ใน Search Console แล้วรอ Google ประเมิน canonical ใหม่ (หลายวันถึงสัปดาห์)

5C. Performance หน้าแรก (พ.ย. 2569)

  • PageSpeed มือถือ 62 (LCP 36.5s): หน้าแรกโหลดรูปต้นฉบับ ~21 MB (hero PNG 4 ภาพ ~2 MB, รูป membership 1.9 MB ถูก preload) และรูปจาก CMS/public ไม่มี cache
  • แก้: รูปหน้าแรกผ่าน Next image optimizer (/_next/image, WebP, ย่อตามขนาดจอ) ด้วย src/lib/imageOpt.ts (ฝั่ง server) + helper ซ้ำใน public/js/main.js (ฝั่ง browser ต้องแก้ให้ตรงกัน; ความกว้างต้องอยู่ใน deviceSizes/imageSizes ของ Next: 256/384/640/828/1080/1920 ไม่งั้น 400); hero ภาพแรก render บน server (fetchPriority=high) ภาพ 2–4 โหลดหลัง load; รูปอื่น loading=lazy; images.minimumCacheTTL 30 วัน; คุณภาพ WebP 3 ระดับ (QUALITY ใน imageOpt.ts และ Q ใน main.js, ต้องอยู่ใน images.qualities = [75, 85, 90] ไม่งั้น 400): hero 75, รูปถ่ายแบรนด์ (โปรแกรม/บทความ/สาขา/membership) 85, แพทย์และใบรางวัล 90 (ที่ 75 ใบหน้า/ตัวอักษรเล็กนุ่มลงเมื่อซูม); ตัวย่อรูปไม่ขยายรูปเล็ก (ความคมถูกจำกัดที่ความละเอียดไฟล์ต้นฉบับ: รางวัล 243 px, แพทย์ 500 px)
  • cache header ใน next.config.mjs: /api/media/file/* 30 วัน, /assets + /logo 7 วัน, /css + /js 1 ชม. (ไฟล์ CSS/JS ไม่มี hash ในชื่อ)
  • ยังไม่ได้ทำ: ลด CSS ที่บล็อกการแสดงผล, width/height ของรูป (CLS 0.059 ผ่านอยู่แล้ว), หน้าอื่นนอกจากหน้าแรกยังใช้รูปต้นฉบับ

5D. ISR / การ cache หน้าสาธารณะ (พ.ย. 2569)

  • หน้าแรกเคยตอบช้า (TTFB ~4 วินาที, Cache-Control: no-store) เพราะ revalidate = 60 ไม่ทำงาน: มี draftMode() ใน (public)/layout.tsx และ headers() ใน [locale]/not-found.tsx ซึ่งทำให้ ทั้ง route เป็น dynamic
  • กฎ: ห้ามใช้ cookies() / headers() / draftMode() / searchParams ใน layout, page หรือ not-found.tsx ของหน้าสาธารณะ ถ้าจำเป็นต้องรู้ภาษาให้ใช้ params หรืออ่านฝั่ง client (เช่น NotFoundByLocale.tsx ใช้ usePathname)
  • ตรวจหลัง deploy: curl -sI https://www.phivaraphyathai.com/th | grep -i -E "cache-control|x-nextjs-cache" ต้องเห็น s-maxage=60 (ไม่ใช่ no-store)
  • รายละเอียด ISR และวิธีไล่หาสาเหตุ: docs/notes/ISR-และการ-cache.md
